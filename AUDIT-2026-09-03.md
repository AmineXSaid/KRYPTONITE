# Genesis extension audit

Branch `claude/genesis-extension-audit-i9qfv8`, HEAD `be9f694`. Six subsystems traced
from user action to effect. Nothing below is asserted from a comment; every claim
cites a line, a command, or an experiment.

## How the code was exercised

`package.json` scripts as they actually are: `test` → `node test/run.js` (directory is
the suite list); `test:package` → package then run the `@requires-package` suites;
`test:mcp`, `test:live` → tagged suites.

| Run | Result |
|---|---|
| `npm test` | 71 suites, 2345 PASS. **1 failed: `mcp-live.ts`** |
| `npm run package` + `node test/run.js vsix render mentions activate-vsix --include-tagged` | 6 suites, 0 failed. `render.cjs` = 376 assertions in real Chromium |
| `node test/run.js mcp-e2e --include-tagged` | 69 PASS, 0 failed (real filesystem + memory servers spawned) |
| Skipped by tag, not run | `attachment-e2e.ts`, `skill-gating-live.ts` (`@requires-network`) |

The `mcp-live.ts` failure is environmental, not a code defect: `npm error code
SELF_SIGNED_CERT_IN_CHAIN` from the sandbox's TLS-intercepting proxy when the
"started from an unrelated workspace" case runs `npx` outside the repo. The earlier
cases in the same suite passed because `node_modules` already holds the servers.

Harness facts confirmed rather than assumed: `test/a11y.cjs` and `test/composer.cjs`
read `media/webview/*` **directly** (a11y.cjs:52-54), so edits there are tested;
`test/render.cjs` reads the `.vsix` (render.cjs:36-37) and drives real Chromium via
`playwright-core` (render.cjs:44,221) — its geometry assertions measure real layout,
not jsdom zeros. The one jsdom geometry assertion I found (`composer.cjs:1113-1130`)
stubs `offsetWidth`/`offsetHeight` explicitly and says so in its own comment. No
vacuous-geometry finding.

**Break tests.** I disabled production gates and re-ran to prove the assertions bite.
All were reverted; `git status` is clean.

| Gate disabled | Result |
|---|---|
| `loop.ts:1371` execution-boundary phase gate | `agent-gate.ts` fails — "and nothing was written" reports `Wrote 1 lines to y.md.` |

## 1. Agents — **sound**

Loading, validation and scope are the strongest part of the codebase I looked at.

Traced: `loadAgents` (`src/agents/loader.ts:411-538`) → `App.agents` →
`SessionController.send` resolves the agent once per turn from *the turn's own
conversation* (`src/ui/session.ts:939`) → `agentAllowsTool` at the call
(`src/agent/loop.ts:1378`) and `agentAllowsMcp` at the call (`src/ui/session.ts:971-976`).

- Malformed YAML → warning, file skipped (loader.ts:441-450). No frontmatter → skipped.
  Bad name → skipped. Duplicate name → first wins, and `entries.sort()` at loader.ts:427
  makes "first" deterministic across filesystems. Missing description/body → warning, loads.
- A malformed `mcp:` key returns `allMcp: false` (loader.ts:363-374) — a typo cannot widen
  reach. `include: []` is distinguished from an absent `include` by `includeActive`
  (loader.ts:52-70). Both of these are the safe direction and both are tested.
- **Scope is enforced at the call, not only at the advertisement.** Proved by break test.
  `ctx.mcp` is a per-turn wrapper (session.ts:960-985) rather than the registry itself,
  precisely so a name the model produced from earlier in the transcript is still checked.
- Agent is **per-conversation** and travels in the transcript; `activeAgent` was
  deliberately excluded from the Kryptonite→Genesis state migration (app.ts:522-528).
  Mid-turn agent change does not affect the running turn (session.ts:930-939).

### Findings

**A1 — an agent with a `skills:` list but no `read_skill` in `tools:` is told to do
something it will be refused for, on every request. (defect, medium confidence in impact)**
`systemPromptFor` injects `skillIndex(skills)` unconditionally (`src/agent/loop.ts:784`),
including the rule "read_skill it first". `agentAllowsTool` then refuses `read_skill`
for any agent whose `tools:` list omits it (loop.ts:1378). The loader warns about the
*exact analogous* case for memory — "told to maintain the file on every request and
refused every time it tries" (loader.ts:508-521) — and has no equivalent check here.
`agentTemplate` puts `tools: [read_file, list_files, glob, search]` and `skills:
[some-skill]` five lines apart (loader.ts:600-607), so the template invites the
combination. Scenario: an agent scoped to reads, given one skill, burns a tool call and
a refusal every turn it decides the skill is relevant.

**A2 — an agent naming a nonexistent or disabled skill gets silence. (risk)**
`enabledSkills` is `on.filter(s => agent.skills.includes(s.name))` (app.ts:1152-1156).
A typo in `skills:` yields zero skills with no warning at load and no warning at use.

## 2. MCP servers — **partially verified**

Traced connect → `tools/list` → call → result → disconnect, plus the failure modes.

- Never comes up: `fail()` (client.ts:517-534) records the **first** reason and rejects
  every pending request; the panel shows `state: "failed"` with a stderr tail.
- Dies mid-session: `exit` handler → `fail()` → pending rejected → `callTool`'s catch
  returns `{isError: true, content: "<server>/<tool> failed: server exited (…)"}`
  (client.ts:476-478). Subsequent calls are refused by `registry.call`'s state check
  (registry.ts:514-519). This is correct.
- Malformed JSON: the line is skipped (client.ts:613-616), by design, because servers
  print banners to stdout. The consequence is the request times out at 60s
  (`DEFAULT_TIMEOUT_MS`, client.ts:280) rather than erroring immediately.
- Output cap: `MCP_OUTPUT_CAP = 60_000` in `capOutput` (registry.ts:534-548), announced
  in-band — the model is told the true size and to narrow the request. `loop.ts:1435`
  applies the same 60k. Images survive the text truncation deliberately.
- Images: `splitContent` (client.ts:761-816) caps per-image, per-result and by count,
  and refuses non-wire media types with the *first* applicable reason. With no vision,
  the caller passes `pixels=false` (session.ts:983) and the model gets `noVisionNote`
  naming the two profile fields that would fix it (client.ts:825-831). This is good.

### Findings

**M1 — `readOnly` is a claim about a *server*, and it opens Ask and Plan to every tool
on that server, writes included. Combined with `approval: "auto"` a workspace can have
unattended writes in Ask mode. (defect / high-severity risk, high confidence)**
`toolAllowedIn` (loop.ts:213-220): in Ask, `mcp__*` is allowed iff
`registry.isReadOnly(name)`, which is per-server (`registry.ts:481-485`).
`runTool` then consults `needsApproval`, also per-server (registry.ts:467-471); with
`approval: "auto"` the call runs with no card. So `{"readOnly": true, "approval":
"auto"}` on a server exposing `write_file` gives an **Ask**-mode turn an unprompted
workspace write. `readOnlyWarnings` (registry.ts:325-357) detects exactly this
disagreement and only writes it to the output-channel log (registry.ts:311) — nowhere
the user is looking. The code documents the per-server design honestly; the enforcement
matches the design; the design is the problem.

**M2 — the Ask system prompt tells the model something `toolAllowedIn` contradicts.
(defect, high confidence)** `ASK_ADDENDUM` at `src/agent/loop.ts:296` says "Do NOT …
call any MCP tool — **none are offered**". `toolAllowedIn` at loop.ts:218 offers every
tool of every `readOnly: true` server in Ask. Two statements in the same file, ~80 lines
apart, disagree.

**M3 — a single MCP frame larger than 8 MB is silently discarded and the call times out.
(defect, low severity, high confidence)** `client.ts:620`: `if (this.buf.length > 8 *
1024 * 1024) this.buf = "";`. A server returning one >8 MB line loses the response
entirely; the pending request then rejects at 60s with "tools/call timed out", which
names the wrong cause. `MCP_OUTPUT_CAP` never gets a chance to run, so the user is
told about a timeout rather than an oversized result.

**M4 — the version reported to every MCP server is wrong. (defect, trivial)**
`clientInfo: { name: "genesis", version: "0.8.0" }` at `src/mcp/client.ts:399`,
`src/mcp/http.ts:83` and `src/mcp/http.ts:375`; `package.json` says `0.9.0`. Hardcoded
in three places rather than derived.

**M5 — `mcp-live.ts` needs the network and is not tagged. (harness defect)**
Its "started from an unrelated workspace" case runs `npx` outside the repo, which must
fetch. It carries no `@requires-network` tag, so `npm test` is not hermetic and fails
on any machine behind a TLS-intercepting proxy or offline.

## 3. Skills — **sound**

- Discovery: one folder per skill with `SKILL.md` (`src/skills/loader.ts:131-170`).
  Duplicate names refused with **both** paths named (loader.ts:152-158). Workspace
  skills shadow bundled ones with a warning (`workspaceConfig.ts:113-132`).
- Disabled skills are excluded **at the data**, not at the display: `enabledSkills`
  filters `disabledSkills` (app.ts:1153), that list becomes `ctx.skills`
  (session.ts:949), and `read_skill` resolves names only against `ctx.skills`
  (tools.ts:1417). A disabled skill is absent from the index *and* unreachable by name.
  Verified by reading both ends, not just the index.
- Bounds: `read_skill` caps the body at 12,000 chars with the truncation stated in-band
  and a pointer to `read_file` (tools.ts:1439-1446). `MAX_BODY_CHARS = 24_000` in the
  loader is only a warning — the enforcement is the read cap, and `test/skill-bounds.ts`
  proves it with a 72k fixture that actually exceeds it.
- Path traversal: `read_skill` takes a *name*, looked up in a list — there is no path to
  traverse. Bundled files are read through `read_file` → `readable()` → `writable()`,
  whose `realpathSync` check (tools.ts:398-415) refuses a symlink escape even when
  `readOutsideWorkspace` is on, because a lexically-contained path takes the strict branch.

### Findings

**S1 — `test/skill-bounds.ts` tests no path bound at all. (coverage gap)**
It covers size, duplicates and the index. Nothing exercises a skill folder that is a
symlink, or a `skillsDirectory` pointing outside the workspace.

**S2 — `loadSkills` reads `SKILL.md` with no containment check, and `skillsDirectory` is
not machine-scoped. (risk, inside the stated trust boundary)**
`workspaceConfig.ts:146` does `loadSkills(path.join(src.root, src.skillsDir))` with
`skillsDir` straight from settings; `loader.ts:141` does a bare `readFileSync`. A
workspace `.vscode/settings.json` setting `"genesis.skillsDirectory": "../../elsewhere"`,
or a symlinked skill folder, puts out-of-workspace file contents into the system prompt.
`caBundlePath` and `searchApiKey` are `scope: "machine"` in `package.json` for exactly
this reason; `skillsDirectory` and `profileDirectory` are not. Mitigated — not removed —
by `untrustedWorkspaces.supported: false`.

## 4. Interaction (transcript, per-message actions) — **defective**

The message context menu implements its `role="menu"` contract properly. The two header
menus that declare the same role implement none of it, and one of them kills a running
turn when you try to dismiss it.

Method: jsdom probes driving `media/webview/sidebar.js` through the same harness
`test/composer.cjs` uses. Outputs quoted verbatim.

### Findings

**I1 — Escape while the More or History menu is open, during a turn, interrupts the turn
and does not close the menu. (defect, high confidence, proven)**
`media/webview/sidebar.js:6716-6725`. Escape is special-cased for `#msgMenu` (6718-6721)
and guarded for the quick-picker (`$("qp").hidden` at 6724). `#morePop` and `#historyPop`
are in neither guard. Probe:

```
Escape with morePop open while running   -> interrupt posted: 1 | morePop hidden now: false
Escape with historyPop open while running-> interrupt posted: 1 | historyPop hidden: false
Escape with the msgMenu open             -> interrupt posted: 0   (correctly guarded)
```

Scenario: mid-turn you open More to export the chat, change your mind, press Escape.
The menu stays up and the turn is stopped. Directly contradicts the comment at
sidebar.js:6717 — "Interrupting a turn because the user wanted to dismiss a menu is the
wrong reading of one keystroke."

**I2 — `#historyPop` and `#morePop` declare `role="menu"` / `role="menuitem"` and
implement no part of the keyboard contract. (defect, high confidence, proven)**
sidebar.js:1041-1062. Probe after clicking `#moreBtn`:

```
morePop role: menu | aria-label: null
focus after opening: BODY          (never enters the menu)
menuitems: 7 | tabindex: [null,null,null,null,null,null,null]   (no roving tabindex)
ArrowDown moved focus: false
Escape closed morePop: false
```

`msgMenuKeys` (sidebar.js:1622-1641) exists and is correct — it is bound to `#msgMenu`
only. The same probe against the message menu, for contrast:

```
msgMenu: focus on open: pop-row | rows: 4 | tabindex: ["-1","-1","-1","-1"]
msgMenu: ArrowDown moved focus: true
Escape with msgMenu open while running -> interrupt posted: 0 | msgMenu hidden now: true
```
 The comment at sidebar.js:1604-1606 states the rule this violates: *"role=\"menu\"
is a promise about the keyboard, and a11y.cjs exists because role=\"tablist\" was once
declared without the contract that goes with it."* `test/a11y.cjs` checks the tablist
contract (a11y.cjs:191-207) and nothing checks these two.

**I3 — "Reject" on a diff card is an unconfirmed, irreversible revert that can also
destroy the user's own edits. (defect, high confidence)**
Button at sidebar.js:3596, no title, no confirmation. Probe: one click posts
`{"turnId":"t1","file":"src/a.ts","decision":"reject","type":"resolveDiff"}`.
Host: `session.ts:1479` `await this.app.shadow?.restoreFile(turn.preHash, file)` —
restores the file to the **pre-turn snapshot**, so any edit the *user* made to that file
while the turn was running is reverted too; on failure the catch does
`fs.rmSync(path.join(root, file))` (session.ts:1483), deleting a file the user may have
created during the turn at that path. The label reads as "don't apply this" but the write
already landed — Reject is a revert, and nothing on the card says so.
Compare `deleteSession` (app.ts:2967-2994), which does this properly: a modal naming the
conversation, its message count, and "cannot be recovered". The rule exists in the
codebase; the diff card does not follow it.

**I4 — "Rewind to here" can restore the workspace with no confirmation. (risk)**
sidebar.js:1648-1653 posts `restoreCheckpoint` and its comment asserts unconditionally:
"The host names the files a restore would change and asks before doing it."
`app.ts:3294` gates that modal on `this.uiConfig.previewDiff !== false`. With the
Control Center's "Preview diffstat before restore" toggle off
(`controlCenter.js:1943`), the row silently restores. The setting is documented at the
toggle; the comment is wrong, and the menu row gives no hint.

**I5 — dismissing the context menu by clicking away drops focus. (defect, minor)**
`closePops` (sidebar.js:1446-1454) hides `#msgMenu` without the focus restoration that
`closeMsgMenu(true)` (sidebar.js:1612-1619) performs. Focus lands on `<body>` and the
next Tab restarts at the top of the panel — the exact problem `openMsgMenu`'s
`tabindex="-1"` (sidebar.js:1584-1586) was added to avoid.

**I6 — `#msgMenu` has no accessible name.** `role="menu"` with no `aria-label` or
`aria-labelledby` (sidebar.js:1374, confirmed by probe). Same for `#morePop`, `#historyPop`.

### What is right, and is the evidence for I1/I3

Menu clamping is real and correct (sidebar.js:1593-1602), keyboard-invoked menus
(Menu key / Shift+F10, `clientX===0`) fall back to the message's own rect
(sidebar.js:6408-6423), and rows are filtered per message kind with `rewind` hidden
when no checkpoint exists (sidebar.js:1566-1572). The Edit row relabels itself to
"Replace draft and edit" when the draft is non-empty (sidebar.js:1573-1576) — the cost
placed on the control, before the click. The **destructive-command permission card** is
exemplary; probe output:

```
class: perm perm-danger
"This can destroy work … This command can discard work that cannot be recovered.
 It is never approved automatically, and it cannot be granted for next time."
buttons: ["Allow once","Deny"]                    (no "Always allow")
non-destructive buttons: ["Allow once","Always allow this command","Deny"]
```

That is the standard the diff card's Reject fails.

## 5. Composer controls — **partially verified**

### Protocol three-way comparison

Mechanical, not eyeballed. 59 `*Msg` members extracted from the `InboundMessage` union
(protocol.ts:679-694); `case` labels extracted from the dispatch (app.ts:2468-3050);
`post("…")` call sites extracted from all three webviews.

- **Declared but unhandled: none.** 59/59 have a case, and there is a `never`
  exhaustiveness check at app.ts:3029.
- **Posted but undeclared: none in `InboundMessage`.** The eight `browser*`/`agent*`
  kinds posted by `media/webview/browser.js` are handled by the browser panel's own
  dispatch (`src/ui/browser.ts:118-179`) — a separate protocol, correctly separate.
- **Handled but never sent: one.** `attachFiles` (protocol.ts:481, app.ts:2513) is dead.
  `#clipBtn` was changed to a renderer-local `<input type=file>` so it works in
  WSL/SSH/Codespaces windows; sidebar.js:6575-6584 documents the change and nothing
  posts the message any more. `pickAndAttach` is still reachable via the
  `genesis.attachFromHost` command, so this is dead protocol rather than dead code.

### Per-control state (probe, all ten ids)

```
no workspace : draft=disabled sendBtn=disabled clipBtn=disabled  others enabled
no endpoint  : draft=disabled sendBtn=disabled clipBtn=disabled modelBtn=disabled
mid-turn     : all enabled
perm pending : all enabled
```

All ten have accessible names. Send↔Stop transitions correctly in both directions
(sidebar.js:4346-4372) and the `aria-label` changes with it, so the state is not conveyed
by icon alone; typing during a run flips it back to Send because the user wants to speak,
not to stop (sidebar.js:6703-6709). Approval mode shows a word ("Manual"/"Edits"/"Auto"),
a per-mode glyph and a hue — not colour alone (sidebar.js:1995-2024, 2066-2090).

### Findings

**C1 — the attachment count cap is enforced on one path and skipped on another.
(defect, high confidence, proven)**
`addAttachment` enforces `ATTACH_COUNT_MAX = 10` (sidebar.js:6052-6060) and every local
path goes through it. The host-driven path does not: `sidebar.js:7221-7222` is
`for (var ai = 0; ai < m.files.length; ai++) S.attachments.push(m.files[ai]);` — a
direct push. Probe:

```
host attachmentsReady with 40 files -> chips in composer: 40
local paste path x40                -> chips in composer: 10
```

Reachable three ways: dragging from VS Code's Explorer (`attachPaths`, capped at 20
paths, app.ts:1514), the `genesis.attachFromHost` command (`pickAndAttach` →
`showOpenDialog({canSelectMany:true})` with **no** path cap, app.ts:1486-1497), and a
`.zip`, which `expandArchive` expands to up to `MAX_ENTRIES = 400` attachments
(app.ts:1571). So: paste an 11th screenshot and you are told "Up to 10 attachments per
message"; drop one zip and you get 400.

**C2 — the full-auto double-press confirmation is defeated by a double-click.
(defect, high confidence, proven)**
sidebar.js:6683-6697 arms the row on first click and commits on the second, with no time
gate, no pointer-target change, and no separate control. Probe — two `click` events on
the row, as a double-click delivers them:

```
two clicks on full-auto row -> setConfig posted:
  [{"key":"approvalMode","value":"full-auto","type":"setConfig"}]
```

The comment above it (sidebar.js:6678-6686) states the threat precisely — "browsing the
sheet to see what the modes were could hand the agent unattended shell access" — and
double-clicking a row while browsing a list is that same accident.

**C3 — Shift+Tab in the composer is swallowed unconditionally. (defect, medium severity)**
sidebar.js:6788-6793 calls `e.preventDefault()` on every Shift+Tab in `#draft` to cycle
phase. Probe: `defaultPrevented: true, setPhase posted: 1`. A keyboard user in the
textarea cannot move focus backwards; forward Tab still works, so it is a one-way trap
rather than a full one. The shortcut is also *only* bound here — the phase segment
itself has no keyboard handling at all (see C4).

**C4 — `role="radiogroup"` is declared twice with no radiogroup keyboard contract.
(defect, high confidence, proven)**
`#phaseSeg` (sidebar.js:1228-1235) and `#permList` (sidebar.js:1345, rows at 2102).
Probe:

```
phaseSeg role: radiogroup | radios: 3 | tabindex attrs: [null,null,null]
aria-checked before ArrowLeft: false,false,true | after: false,false,true | changed: false
permList role: radiogroup | rows: 3
aria-checked before ArrowDown: true,false,false | after: true,false,false | changed: false
```

No arrow-key navigation, and no roving tabindex — all three phase radios are separate tab
stops. `aria-checked` is kept accurate, which is what the comment at sidebar.js:1224-1227
defends the role on; that is half the contract.

**C5 — `#agentBtn` declares a popup it never reports the state of, and its picker is
mouse-only when opened from the button. (defect, minor)**
sidebar.js:1297-1300 sets `aria-haspopup="menu"`. Probe after clicking it:

```
qp hidden: false | role: listbox | options: 3
focus after opening agent picker: BODY
agentBtn aria-expanded: null | aria-controls: null
ArrowDown on body -> active option changed: false
```

Three problems in one: `aria-haspopup="menu"` names the wrong role (`#qp` is a
`listbox`), `aria-expanded` is never set (every other popup owner sets it —
sidebar.js:2260, 4751, 6317, 6326), and `openAgentPicker` (sidebar.js:4637-4642) does not
move focus, while the arrow keys live in `onDraftKey`. `#permBtn` has the same
`aria-haspopup="menu"` mismatch — its popup is `role="dialog"` (sidebar.js:1338).

### What is right

Attachment *content* handling is careful: no size cap by deliberate decision, documented
at both ends (app.ts:1645-1663, sidebar.js:6003-6011) after two copies of a 10 MB limit
disagreed; binary files are detected by NUL/U+FFFD ratio and reported rather than sent
(`decodeTextAttachment`, session.ts:2415-2427); large text pastes become files at 8,000
chars; the document cancels drag/drop everywhere except the composer, because a webview's
default action for a dropped file is to navigate to it (sidebar.js:6083-6098). The mode
sheet's focus trap (sidebar.js:2154-2183) is a real capture-phase trap with a documented
measurement behind it ("8 of 12 Tab presses left the sheet").

## 6. Modes and transitions — **defective**

### (a) Phase — the single-gate claim holds

`toolAllowedIn` (loop.ts:213-220) is genuinely the only decision point.
`grep -rn runTool src/` finds exactly one production call site — loop.ts:1381, inside
`invoke`, behind both gates. There is exactly one `ToolContext` construction
(session.ts:941) and one `runAgent` call (session.ts:1124). `runOneShot`
(`src/agent/oneShot.ts`) takes the other path and has no tools at all. Break test above
confirms the execution boundary bites.

Phase is resolved **once per turn**: `const phase = opts.phase ?? "act"` (loop.ts:817),
never reassigned; `session.ts:874` captures `this.app.phase` at the top of `send()`.
A mid-turn phase change cannot widen a running turn.

What each phase permits, checked tool by tool rather than trusting the lists:
`ASK_ONLY` = `read_file, list_files, glob, search, read_skill` — all read-only.
`READ_ONLY` adds `update_todos`, which mutates session state (not the workspace) and is
documented as such (loop.ts:166-170). Everything else, `web_search` and `fetch_url`
included, is refused in Ask and Plan. The only way to reach a mutation is M1/M2 above.

**P1 — phase is global; agent is per-conversation. (defect, high confidence)**
`App.phase` is one field (`app.ts:435`) read by every conversation. `agentName(turn.id)`
is per-conversation (session.ts:390). Switching conversations does not change the phase,
and `sessionSwitched` carries none. So plan-mode work in chat A and act-mode work in chat
B share one setting, and approving a plan in A (app.ts:2555-2557 sets
`this.phase = "act"` globally) moves B to Act too. Given the effort spent making the
agent per-conversation (commit "Give each conversation its own agent", app.ts:522-528),
this is an inconsistency rather than a considered choice.

**P2 — phase resets to `act`, the most permissive value, on every extension-host
restart. (risk)** `phase: Phase = "act"` (app.ts:435) is in-memory only; nothing writes
it to `workspaceState`. It survives a *webview* reload — which is what the comment at
app.ts:305 is about, and there it is accurate — but a window reload silently returns an
Ask session to Act. The webview picks the value up from `stateSync`, so it is visible
rather than silent; still, the default on restart is the one that can write.

### (b) Approval mode — host-enforced, but persisted where it can be committed

Enforcement is real and host-side: `requestApproval` (session.ts:1503-1553) is consulted
by `ctx.approve` at every mutating call site, not by the webview withholding a button.
The design is better than its name suggests: `classify(commandOf(summary))` runs
**before** the mode (session.ts:1530-1532), so `destructive` commands raise a card even
in full-auto, and `resolvePermission` refuses to store an "always allow" grant for one
(session.ts:1594-1600). Grants are keyed on the whole command line, not the first token
(`commandOf`, session.ts:2390-2392) — a grant on `npm test` does not cover `npm publish`
— and non-command grants are keyed by `ApprovalKind` from the call site rather than by a
prose prefix (session.ts:1602-1607).

**P3 — `approvalMode` is written to `ConfigurationTarget.Workspace`, i.e. into
`.vscode/settings.json`. (defect / significant risk, high confidence)**
`app.ts:3272`. It persists across sessions, and `"genesis.approvalMode": "full-auto"` is
a committable, clonable line in the repository — inherited by anyone who opens that
workspace, with no prompt and no re-confirmation. `caBundlePath` and `searchApiKey` are
`scope: "machine"` in `package.json` specifically to stop workspace-scoped writes;
`approvalMode`, which governs every side effect, is not. On my reading `ask` is the right
default (it is), but "persists silently at workspace scope" is the wrong persistence for
the most permissive value.

**P4 — an approval-mode change mid-turn widens the turn that is already running.
(defect, medium confidence on severity)** `const mode = this.app.approvalMode()` is read
per call (session.ts:1510), not per turn — the opposite of phase (loop.ts:817) and agent
(session.ts:939), both of which are pinned once "because an agent edited mid-turn should
not change what the turn is allowed to do halfway through it". Switching to full-auto
while a turn runs silences every remaining approval in it. Arguably intended; it is
undocumented and inconsistent with the two neighbouring decisions.

Plus **C2** above: entering full-auto takes one double-click.

### (c) Plan → Act handoff — the approved plan is not what arrives

**P5 — a plan longer than 20 steps, or with a step over 200 characters, is silently
truncated between the card the user approved and the message Act receives. (defect, high
confidence, proven)**
`approvePlan` (session.ts:2151-2164) builds the Act message from
`normaliseTodos(steps)`, and `normaliseTodos` (tools.ts:983-995) does `.slice(0, 20)` and
`String(content).slice(0, 200)`. The card renders the *raw* `steps` from `planProposed`
(session.ts:1318-1323 → sidebar.js:4060-4074) and its header says "N steps".
I drove a real `App` through `approvePlan` with a 25-step plan:

```
steps the plan card shows: 25
step 3 length as shown: 308
todos seeded: 20
message to Act mentions 'Step 20': true
message to Act mentions 'Step 21': false
message to Act mentions 'Step 25': false
step 3 length in the message: 200
does the message say anything was dropped: false
```

The user approves 25 steps and Act is told 20, one of them cut mid-sentence, with nothing
saying so. The comment at session.ts:2160-2163 justifies normalising ("a plan longer than
the cap would instruct Act to work through more steps than the todo card can hold") and
does not notice that the *card* has already shown them all.

**P6 — `test/plan-handoff.ts:136-137` is named for a property its fixture cannot reach.
(coverage gap, high confidence)** "the message carries every approved step" is asserted
with `propose(app, ["One", "Two", "Three"])` (line 122) — three steps against a cap of
twenty. The assertion is real for three steps; the name claims a general property, and
P5 is what it fails to catch.

### (d) Permission requests — sound

- Resolved exactly once: `resolvePermission` deletes before resolving (session.ts:1588-1590);
  `stopTurn` scopes its denials to `entry.turnId !== turn.id` (session.ts:1819-1823) after
  a bug where Stop in one chat denied every card in every chat; `dispose` settles the rest
  (session.ts:2317-2318). No path leaves a promise dangling.
- Webview reload while pending: the card is a `ReplayableEvent` emitted through the turn
  (session.ts:1574-1581), so it is buffered and replayed. `raiseApproval`'s only call site
  (session.ts:1090) always passes a turn, so the unbuffered `broadcast` branch is
  unreachable — the promise cannot be orphaned by a reload.
- Conversation switch while pending: deliberately left pending (`detach`, session.ts:2277-2292),
  replayed on return. Documented and correct.
- **P7 — any surface can resolve any request. (risk, low severity)** `emit` →
  `app.broadcast` → **all** sinks (app.ts:911-913), so the Control Center webview receives
  every `permissionRequest` including its id, and `dispatch` performs no `source` check
  (app.ts:2587). It never renders them today, so this is a latent design gap, not a live
  exploit — but the `source` parameter is already threaded through `handleMessage` and
  unused for this.

## The three to fix first

1. **C1 — the attachment cap bypass at `media/webview/sidebar.js:7222`.** One line, no
   design decision required (route `attachmentsReady` through `addAttachment`), and it is a
   cap the product advertises to the user's face and then does not apply. A dropped zip
   currently puts up to 400 attachments into one request. Lowest cost, highest
   embarrassment.

2. **P5 — the plan truncated between approval and Act (`src/ui/session.ts:2151`).** This is
   the one finding where the user is shown one thing and the system does another with no
   signal. Everything else in this report either fails loudly or fails within its own
   stated design; this quietly substitutes a 20-step plan for the 25-step plan someone read
   and agreed to. Either cap the *card* to what will survive, or send `steps` in full and
   let the todo list be the shorter view — but the two must not disagree in silence.

3. **I1 — Escape interrupting a turn from the header menus
   (`media/webview/sidebar.js:6724`).** Cheap to fix (extend the existing guard to
   `#morePop`/`#historyPop`), and the failure is destructive of work in progress and
   completely unexpected: the user's dismissal gesture kills the turn *and leaves the menu
   open*. It also comes with I2 for free — giving those two menus the keyboard contract
   their role already promises fixes both.

Runners-up, in order: **M1/M2** (a `readOnly` + `approval: auto` MCP server can write from
Ask mode, and Ask's own prompt says it cannot) — the reason it is not top three is that it
requires a specific configuration the user wrote deliberately, whereas 1–3 need no
configuration at all. Then **P3** (full-auto persisted at workspace scope) and **C2**
(full-auto entered by double-click), which compound: the setting is one accidental
double-click away and then lives in a file that gets committed.
